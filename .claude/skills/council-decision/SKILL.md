# Council Decision

## 何时用
看到自己在"选 A 还是 B"——不管多小——就用。判断标准:这个选择如果错了,需要一个 PR 来回滚吗?需要就开 ADR。

## 流程
1. 复制 `docs/adr/0000-template.md` 为 `docs/adr/NNNN-<slug>.md`(NNNN 递增)。
2. 先写"问题"和"选项",再写议会。**先有选项,再有意见**,避免先有结论再找理由。
3. 四个角色依次写。每个角色三行:判断 / 证据来源 / 对其他角色的回应。
   - 证据来源是**具体的**:文件名 + 哪一条;论文名;审核指南条款号;设计稿哪一屏。
   - 没有证据就写"无证据,仅直觉",并把置信度标低。
   - 产品经理需要新证据时,调用 `appstore-review-research` 技能抓取,而不是凭印象。
4. 角色必须互相回应。至少一处"我反对 X 的理由是…"或"接受 X 的意见,因此…"。
5. 结论:
   - 一致 → `accepted`,在 PR 描述里链接该 ADR。
   - 冲突且是**产品**问题(定价、文案、功能取舍)→ `needs-human`,写一句话冲突点,停止相关工作,继续做不依赖此决定的任务。
   - 冲突且是**技术**问题 → iOS 工程师视角仲裁,注明"技术仲裁"。
6. ADR 超过一页 = 还没想清楚,回到第 2 步压缩选项。

## 反模式
- 四个角色说同样的话(没有真正换视角)。
- 引用"用户喜欢"却没有 reviews-findings.md 的条目。
- 把 needs-human 的问题自己拍板。
